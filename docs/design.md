## 1. Цель и границы

Первый законченный сценарий: открыть сайт → без аккаунта пройти 2–4 текста → получить рекомендацию → при желании изменить сложность → зарегистрироваться или войти и сохранить результат. При отказе от регистрации результат остаётся доступен в этом браузере до истечения анонимной сессии.

Проект служит обучению владельца backend-разработке и портфолио для middle-собеседований. Приоритет — распространённые технологии и объяснимые решения. Основные демонстрируемые задачи: детерминированная бизнес-логика, API-контракты, транзакции, идемпотентность повторных ответов, права доступа и интеграционные проверки.

В этот этап не входят уроки, оценивание знаний по CEFR, кабинеты со статистикой, редактор контента, награды, очереди, микросервисы и ИИ-проверка. Небольшой экран сохранённого результата и вход в аккаунт входят, поскольку без них сохранение нельзя продемонстрировать. Повторное прохождение из того же активного браузерного сеанса отдельной кнопкой пока не добавляем; новая анонимная сессия может пройти подбор заново. Историю ранее привязанных прохождений сохраняем.

Критические свойства: результат не исчезает при обновлении страницы, повторный запрос не создаёт второй ответ, чужое прохождение недоступно, обновление текстов не меняет смысл прошлых результатов. Потеря cookie анонимного браузера не позволяет восстановить доступ; это явно сообщаем до регистрации.

## 2. Подходы и предлагаемый стек

Рассматривались Django с серверными страницами и FastAPI с отдельным интерфейсом. Django уменьшает объём интеграции стандартных компонентов. Пользователь выбрал FastAPI для учебных и карьерных целей. Сравнительный рейтинг рынка не исследовался.

| Компонент | Предложение | Зачем нужен |
| --- | --- | --- |
| Backend | Python 3.13 + FastAPI, Pydantic | JSON API, валидация контрактов и документация OpenAPI |
| Данные | PostgreSQL | Долговечные результаты, ограничения целостности и блокировки строк |
| Доступ к БД | SQLAlchemy 2, синхронный psycopg 3 | Явные транзакции и типизированные модели |
| Миграции | Alembic | Воспроизводимые изменения схемы |
| Интерфейс | React + TypeScript, сборка Vite | Выбор слов и состояния формы без ручной синхронизации DOM |
| Пароли | pwdlib с Argon2 | Готовое хеширование и проверка, без собственной криптографии |
| Проверки | Имеющиеся Ruff, mypy, pytest; HTTPX и Playwright для интеграции и браузера | Проверки бизнес-правил, API и полного пути |
| Запуск | Один backend-процесс, статическая сборка интерфейса, PostgreSQL | Минимальное число рабочих компонентов |

React выбран как предложение ради распространённого подхода и понятной модели состояния интерактивного экрана. Альтернатива — обычный TypeScript с DOM: меньше зависимостей, больше ручного управления состояниями. SSR и frontend-сервер в production этому сценарию не нужны. Дополнительные библиотеки состояния/запросов не обязательны: локальное состояние компонентов и fetch достаточны.

Синхронный доступ к БД выбран ради простых транзакций и отладки. Обработчики с блокирующей БД — обычные `def`; не вызываем их из `async def` как блокирующие функции на event loop. Отдельный SQLAlchemy Session на запрос, без глобальной разделяемой сессии. Это не заявление о производительности; целевую нагрузку и измерения определим отдельно.

Версии зависимостей закрепляются при подготовке плана по совместимости с Python 3.13 и актуальной официальной документации. Этот документ не разрешает их установку. Redis, JWT, брокер сообщений и отдельная админка в этом сценарии не требуются.

## 3. Языковая модель и алгоритм

Полный контент, подсчёт, переходы и точные тексты интерфейса находятся в [onboarding-content.md](onboarding-content.md). Здесь — технический контракт этих правил.

- Нормализация `surface-v1`: регистр игнорируется, апострофы унифицируются, разные словоформы не объединяются. Повторы в одном тексте имеют общий `word_id`; исходное отображение сохраняется.
- Авторские сегменты имеют вид `text` или `excluded`; код, идентификаторы и числа исключаются по явной разметке. Публикационная проверка запрещает непомеченные неподдерживаемые фрагменты. В текущих пяти текстах исключаемых фрагментов нет.
- `U` — число выбранных уникальных ID, `N` — число всех учитываемых ID. Доступность: `100 * U <= threshold_percent * N`, по умолчанию `threshold_percent=20`. `N=0` запрещено при публикации.
- Ответ — либо `unknown_words` с непустым множеством `word_ids`, либо `all_known` с пустым списком. Смешанные и неявные пустые ответы запрещены.
- Вычисление и переход выполняет только сервер. Клиент не присылает уровень, проценты, знаменатель или ID следующего текста.

| Текст | Доступен | Трудный |
| --- | --- | --- |
| start | installation | simplified |
| simplified | foundations / simplified_accessible | foundations / simplified_difficult |
| installation | parameters | foundations / start_accessible |
| parameters | constraints | basic_docs / installation_accessible |
| constraints | complex_texts / constraints_accessible | confident_reading / parameters_accessible |

В ячейках с `/` указаны конечная рекомендация и причина результата. Все ветви конечны: шесть маршрутов, максимум четыре ответа. Уточняющий текст всегда завершает подбор. Оба его исхода дают самый начальный маршрут с разными пояснениями; дополнительного уровня нет.

Рекомендация `recommended_level` неизменяема после завершения. Выбор `selected_level` первоначально равен рекомендации, затем может меняться независимо. Причина и результаты отдельных текстов сохраняются. Пользователь видит, где рекомендация системы, а где его выбор.

## 4. Контент и версионирование

Храним опубликованный пакет контента в БД, исходный авторский JSON — в репозитории. Служебная команда валидации/импорта доступна разработчику, не через публичное API. Пакет включает пять текстов, порядок сегментов, токены, таблицу переходов, четыре уровня и русские пояснения. Контент здесь — обычный текст, а не исполняемый HTML.

Идентификаторы: `bundle_version`, `normalization_version`, `policy_version`; пакет имеет хеш содержимого. Первые значения — `onboarding-v1`, `surface-v1`, `routing-v1`. Порог — целое число 0–100, копируется в новую попытку вместе с версиями. Даже изменение порога не меняет начатое прохождение.

Публикация нового пакета создаёт новую запись и переключает указатель активной версии в одной транзакции. Опубликованные записи не редактируются. Начатые и завершённые прохождения ссылаются на старую версию; удаление используемой версии запрещено внешними ключами. Повторный импорт того же ID с тем же хешем — без изменений; с иным хешем — ошибка. Проверяем уникальность word_id в тексте, соответствие токенов исходному тексту, отсутствие пустых текстов и достижимость всех конечных ветвей.

Публичный API выдаёт только текущий текст и данные своего прохождения. Во время подбора не отдаём весь пакет, переходы или будущие тексты. Здесь нет ключей правильных ответов: отметка слов — самооценка. Контракты будущих учебных упражнений проектируются отдельно.

## 5. Экраны и поведение браузера

1. Старт: краткое объяснение 2–4 текстов, необязательность регистрации, кнопка начала. При существующем прохождении показываем «Продолжить» либо результат.
2. Текст: номер шага, инструкция, кликабельные слова и две взаимоисключающие формы отправки. Все повторы выбранного написания подсвечиваются вместе. При наличии выбранных слов доступно «Продолжить», при отсутствии — «Все слова знакомы».
3. Отправка: блокируем повторное нажатие и изменение выбора до ответа. При ошибке возвращаем редактирование, сохраняем выбор и разрешаем повторить тот же запрос. Клиент не предполагает, что запись не произошла.
4. Результат: рекомендация, пояснение причины, выбранная сложность, изменение выбора, предложение регистрации/входа. Нет работающих ссылок на отсутствующие уроки. «Пока не сейчас» закрывает предложение, оставляя результат.
5. Регистрация/вход: поля логина и пароля, сохранённый результат доступен и после нового входа. После входа в уже существующий аккаунт перенос нового анонимного результата требует явного действия «Сохранить этот результат в аккаунте».

Слова реализуются доступными элементами управления с клавиатурой и `aria-pressed`; состояние не обозначаем только цветом. Обеспечиваем видимый фокус, удобные области нажатия и перенос длинных строк на мобильном экране. Сообщения загрузки и ошибок доступны экранному диктору. Дизайн проверяем в браузере на узком и широком экране при реализации.

При загрузке получаем контекст браузера и авторитетное состояние с сервера. Отправленные ответы восстанавливаются полностью. Неотправленный выбор сохраняем в sessionStorage по `run_id + step_id + content_version`, без токенов и паролей. Восстанавливаем его только если сервер вернул тот же неотвеченный шаг; иначе удаляем. При недоступном sessionStorage приложение работает, но черновик после перезагрузки теряется. На новом шаге React-состояние сбрасывается по `step_id`. Устаревший сетевой ответ не должен заменять более новую `revision`.

Нельзя вернуться и переписать уже отправленный ответ; кнопка браузера «назад» при восстановлении снова показывает текущее серверное состояние. Открытие двух вкладок обрабатывается как конкурентная работа с одним прохождением.

## 6. Модель хранения

Названия таблиц — ориентир для плана, поля ниже описывают обязательные данные и ограничения.

| Сущность | Основные данные и ограничения |
| --- | --- |
| content_bundles | Уникальная версия, хеш, версии нормализации/политики, неизменяемый JSON со всеми текстами/словами/переходами/пояснениями |
| content_settings | Единственная строка с активной опубликованной версией и порогом для новых прохождений |
| users | UUID, уникальный нормализованный логин, хеш пароля, current_run_id, created_at |
| browser_sessions | UUID, тип anonymous/authenticated, уникальный SHA-256 хеш случайного токена, user_id для авторизованной, CSRF-секрет, created_at/expires_at/revoked_at |
| onboarding_runs | UUID, anonymous_session_id, nullable user_id, версия пакета/нормализации/политики и порог, status, current_step_id, recommended_level, selected_level, reason_code, revision, created_at/completed_at/claimed_at/expires_at |
| onboarding_steps | UUID, run_id, ordinal 1–4, text_id, nullable mode/word_ids/U/N/accessibility/answered_at; UNIQUE(run_id, ordinal), UNIQUE(run_id, text_id) |

`onboarding_steps` одновременно описывает выданный шаг и неизменяемый ответ, чтобы не создавать отдельную сущность без необходимости. Поля ответа либо все заполнены, либо все отсутствуют. В `word_ids` хранится отсортированный список без повторов; членство проверяется по закреплённому пакету. Один неотвеченный шаг на активное прохождение, один run на анонимную сессию: ограничения БД и проверки транзакции. `status` — active/completed; истечение вычисляется по сроку, а не требует фонового изменения статуса.

Результат появляется только вместе с последним ответом в одной транзакции. `revision` растёт при изменении состояния/выбора/владения. `users.current_run_id` указывает на принадлежащее этому пользователю завершённое прохождение; проверяется транзакцией и составным внешним ключом или эквивалентным ограничением схемы. Старые связанные результаты не перезаписываются.

Уникальность логинов обеспечивается в БД. Связанные попытки и версии контента не удаляются каскадом при очистке анонимных сессий. Для всех времён — UTC с timezone. Не храним IP в истории обучения и не пишем пароли, cookie, CSRF-токены или тела регистрационных запросов в логи.

## 7. API-контракты

Все пути ниже начинаются с `/api/v1`. JSON использует английские идентификаторы. Ошибка содержит стабильный `code`, безопасное `message`, `request_id`; валидация указывает поля без отражения пароля. Для ответов с сессиями и результатами — `Cache-Control: no-store`. Лимит JSON-запроса — 16 KiB; после проверки владения длину массива ID и членство слов проверяем по тексту переданного `step_id` в закреплённой версии run, включая повтор старого ответа. Текущий шаг не используется для проверки слов старого шага. Лишние поля отвергаются.

| Метод и путь | Вход | Результат |
| --- | --- | --- |
| POST /browser-session | Пустой объект; допустимый Origin | Создать/переиспользовать анонимную cookie, вернуть CSRF-токен; повтор с действующей cookie не создаёт новую сессию |
| GET /context | Cookie | Наличие аккаунта, CSRF-токены действующих сессий, ID текущего анонимного и сохранённого прохождений; при отсутствии — пустой контекст |
| POST /onboarding | Анонимная cookie и CSRF | Начать либо вернуть единственный run этой анонимной сессии с первым/текущим шагом; 201 при создании, 200 при повторе |
| GET /onboarding/{run_id} | Cookie владельца | Авторитетное состояние run с revision и текущим шагом либо результатом |
| POST /onboarding/{run_id}/answers | step_id, mode, word_ids, content_version; cookie и CSRF | Сохранить ответ и вернуть текущее состояние run; 200 также при повторе того же ответа |
| PUT /onboarding/{run_id}/selection | selected_level, expected_revision; cookie и CSRF | Изменить выбор в завершённом run; 200 с новой revision |
| POST /auth/register | username, password, run_id; анонимная cookie и CSRF; нет действующей auth-сессии | Создать пользователя, привязать завершённый результат, выдать новую auth-cookie и отозвать анонимную; 201. При действующей auth-сессии — 409 already_authenticated без изменений |
| POST /auth/login | username, password; анонимная cookie и CSRF | Проверить пароль, выдать/сменить auth-cookie; 200. Анонимный результат сохраняется отдельно до явного переноса |
| POST /onboarding/{run_id}/claim | expected_revision; обе cookie и auth-CSRF | Привязать свой анонимный завершённый run к аккаунту, сделать текущим; 200; повтор для того же владельца безопасен |
| POST /auth/logout | auth-cookie и auth-CSRF | Отозвать auth-сессию, удалить cookie; 204. Повтор без сессии с допустимым Origin — 204 |

Состояние активного run: `id, status, revision, bundle_version, expires_at, step {id, ordinal, text_id, segments}`. Сегменты дают исходную строку и nullable `word_id` для выбора. Токены/сегменты полностью формирует сервер; клиент не токенизирует английский текст заново. Состояние завершённого run вместо шага содержит `recommended_level, selected_level, reason_code, explanation, saved_to_account`. Контекст не содержит секретов доступа: CSRF-токены не заменяют HttpOnly-cookie.

Основные ошибки: 401 — нет действующей авторизации для операции аккаунта; 403 — CSRF/Origin; 404 — чужой или неизвестный run/step; 410 — своё истёкшее анонимное прохождение при ещё проверяемой cookie; 409 — другой ответ на уже отвеченный шаг, устаревшая revision, неверная стадия, занятый логин или регистрация при действующей auth-сессии; 422 — неверный формат, неизвестные word_id текста переданного шага, конфликт mode и списка; 429 — превышен лимит; 503 — временно недоступна БД. Для чужого ресурса не раскрываем стадию и факт истечения. Если cookie уже удалена браузером, неизвестный run даёт 404, а UI объясняет отсутствие сохранённого анонимного сеанса.

`GET` результата до завершения возвращает активное состояние, без вымышленной промежуточной рекомендации. Передаваемый `content_version` обязан совпасть с версией run; несовпадение — 409 `content_version_mismatch`, клиент перечитывает состояние. Типы ответа описываются в OpenAPI как различимые варианты active/completed.

## 8. Повторы, конкурентные запросы и сбои

**Начало:** в транзакции блокируем строку анонимной сессии, проверяем срок и отзыв, возвращаем существующий run либо создаём run и первый step. UNIQUE(anonymous_session_id) страхует гонку. Потеря ответа до установки самой первой cookie может создать пустую осиротевшую сессию; учебных ответов в ней ещё нет, очистка удалит её позже.

**Отправка:** одна транзакция; блокируем сессию, затем run, повторно проверяем доступ и сроки. Ищем step только внутри этого run. Валидируем канонический ответ по его исходному тексту и версии, независимо от текущего шага run. Если step уже отвечен тем же mode и множеством ID, ничего не меняем и возвращаем текущее состояние run, даже если он уже завершён. Если корректно сформированный ответ отличается — 409 `answer_already_recorded`; некорректные ID/формат — 422. Для нового ответа step должен быть текущим. Сохраняем ответ, создаём следующий step либо результат, увеличиваем revision и коммитим до успешного HTTP-ответа.

Разный порядок ID не создаёт другой ответ; повторяющиеся ID отвергаем как 422, а не увеличиваем U. Число U клиент не задаёт. Неверный ответ не создаёт ни новой строки, ни перехода.

Повтор возвращает актуальное состояние, а не сохранённый старый HTTP-пакет: другая вкладка могла пройти дальше. Клиент сверяет revision. Ответы не требуют отдельной таблицы idempotency keys: ключом бизнес-операции служит step_id с неизменяемым ответом. До коммита сбой откатывает всё; после коммита и потери ответа повтор находит уже сохранённый ответ.

**Изменение выбора:** блокировка run и сравнение expected_revision. При совпадении — присваиваем выбранное значение; то же значение не увеличивает revision. При устаревшей revision и уже установленном таком значении возвращаем 200 без записи; при другом значении — 409 и перечитывание. Это позволяет повторить потерянный ответ и не перетереть более новый выбор.

**Регистрация/перенос:** атомарные операции описаны ниже. Общий порядок блокировок: строки browser_sessions по ID, затем users, затем onboarding_runs по ID. Чтение аутентификации внутри изменяющей транзакции повторно проверяет срок/отзыв. Нельзя доверять предварительно загруженному состоянию до блокировки. Не держим транзакцию во время сетевых вызовов; хеширование пароля выполняется до блокировок, затем предпосылки проверяются заново.

Все пользователи редактируют только свои run. UUID не является разрешением доступа. При недоступной БД не возвращаем успех из памяти. Автоматического бесконечного повтора транзакций нет; временная ошибка возвращает 503 и допускает ограниченный повтор пользователем.

## 9. Аккаунты, сессии и привязка

Предложение для небольшого первого этапа: логин и пароль, без сбора email. Логин 3–32 ASCII-символа `[a-z0-9_]`, перед проверкой обрезаем крайние пробелы и приводим к нижнему регистру. Пароль 15–128 символов, не обрезаем и не нормализуем, разрешаем вставку из менеджера. Проверку/хеширование выполняет pwdlib с Argon2; параметры библиотеки уточняются в плане. Вход даёт одно сообщение для отсутствующего логина и неверного пароля; выполняется проверка против фиктивного хеша при отсутствующем пользователе.

Существенное ограничение этого предложения: восстановления забытого пароля и email-подтверждения пока нет; явно сообщаем об этом при регистрации. Для этапа с полноценными уроками нужно отдельно решить восстановление аккаунта. Это ограничение принято в составе общего утверждения дизайна; восстановление аккаунта остаётся за границами этого этапа.

Используем две разные непрозрачные cookie: anonymous и authenticated. Токены — 32 случайных байта из криптографического генератора; в БД хранится только SHA-256 хеш. Auth-сессия всегда создаётся с новым токеном при входе; анонимная никогда не превращается в авторизованную с тем же токеном. Production-cookie: HttpOnly, Secure, SameSite=Lax, Path=/, без Domain, с префиксом `__Host-`. Сроки контролирует сервер: 7 суток с создания; без скользящего продления. Локальное HTTP-окружение использует отдельные имена cookie, production не ослабляет флаги.

Для изменений проверяем точное совпадение Origin с настроенным origin сайта и заголовок `X-CSRF-Token` против секрета соответствующей серверной сессии. Missing/чужой/`null` Origin запрещён на изменяющих браузерных API. Начальное создание anonymous-cookie проверяет Origin, остальные гостевые изменения — ещё и guest-CSRF. Login/register требуют guest-CSRF; после входа действия аккаунта используют auth-CSRF. CORS для произвольных origins не включаем. JSON и SameSite — дополнительные меры, не замена проверки. В dev frontend проксирует `/api` на backend, сохраняя одну origin-модель.

**Регистрация:** допускается для своего завершённого анонимного run, только если в запросе нет действующей auth-сессии. При действующей auth-cookie возвращаем 409 `already_authenticated`, не меняя ни аккаунт, ни сессии, ни run; UI предлагает сохранить результат в текущий аккаунт или сначала явно выйти. Истёкшая/отозванная auth-cookie не считается действующей. В одной транзакции создаются user и auth-session, run получает user_id/claimed_at и бессрочное хранение, users.current_run_id устанавливается, guest-сессия отзывается. Cookie выставляется после коммита. При потере ответа аккаунт и результат уже сохранены: повторная регистрация не создаёт дубликат благодаря проверкам стадии и уникальному логину; UI предлагает войти теми же данными. Перед входом при отозванной guest-cookie UI создаёт новую анонимную сессию и получает её CSRF-токен; уже сохранённый результат восстанавливается через аккаунт. Не выдаём старую auth-cookie по отозванной guest-cookie.

**Вход существующего пользователя:** новая auth-сессия создаётся после проверки пароля, предыдущая auth-сессия этого браузера отзывается. Guest-cookie остаётся действующей только для её анонимного результата. Если есть новый guest-run, показываем его и действие «Сохранить этот результат в аккаунте»; поясняем, что он станет текущим, прежний результат останется сохранён. До явного claim указатель аккаунта не меняется.

**Claim:** требуются действующий аккаунт и guest-cookie владельца run. В транзакции проверяем completed, unowned, сроки и expected_revision; устанавливаем owner и current_run_id, отзываем guest-session. Уже принадлежащий этому же аккаунту run — безопасный повтор 200 без изменения current_run_id: другой перенос мог стать текущим позже. При другом владельце — 404. Авторизованный владелец может читать и менять свой run без старой guest-cookie. Для claim после потери ответа сначала проверяем владельца по auth-сессии; отозванная guest-cookie не мешает безопасному повтору.

**Сроки:** анонимный run доступен до expires_at исходной guest-сессии. Нельзя зарегистрировать/перенести истёкшее прохождение. Сохранённый в аккаунт run не истекает вместе с cookie; новый вход восстанавливает доступ. Очистка по расписанию на хосте удаляет не привязанные run и их ответы спустя 30 дней после истечения; затем ненужные сессии без ссылок. Отозванные сессии с историческими ссылками могут сохраняться как запись без права доступа. Удаление аккаунта и политика долгосрочного хранения — отдельное требование перед дальнейшим расширением продукта.

Перед публичным запуском включаем ограничения регистрации, входа и создания анонимных сессий на reverse proxy: исходные настройки 5 запросов входа/регистрации в минуту с IP, 10 созданий сессии/начала в минуту, с небольшим burst 5; клиент получает 429 и Retry-After. Значения — эксплуатационные настройки для демо, а не защита от всех атак; общий IP может ограничить нескольких пользователей. Заголовки адреса клиента принимаем только от доверенного proxy. Точную конфигурацию проверяем отдельно на выбранном хосте. Массовое распределённое злоупотребление этим не решается.

## 10. Структура приложения и размещение

Backend — один модульный сервис: `api` (контракты/роуты), `onboarding` (чистые правила и сценарии), `accounts` (вход/сессии), `storage` (модели/транзакции), `content` (валидация/импорт). Чистая функция перехода не зависит от FastAPI или ORM. Не вводим универсальные repository/event-bus абстракции без конкретной потребности.

Интерфейс — отдельный каталог в том же репозитории. Production: один HTTPS-origin, reverse proxy отдаёт статическую сборку и проксирует `/api` в FastAPI; PostgreSQL закрыта от публичного доступа. Локальная БД и интеграционные тесты используют PostgreSQL той же major-версии, что хостинг, не SQLite-замену.

Предлагаем контейнерный запуск backend и PostgreSQL для воспроизводимости, с постоянным томом БД; frontend собирается один раз. Нужность контейнера proxy и точный способ TLS определяются в плане размещения. Не выбираем платный тариф и не создаём облачные ресурсы без бюджета/разрешения. Конкретный хост и домен — оставшееся инфраструктурное решение перед публикацией, не блокирующее локальную реализацию после общего согласования.

Миграции выполняются явно перед запуском новой версии, не одновременно каждым worker. Пакет контента импортируется отдельной командой. При ошибке миграции выпуск прекращается. Изменения схемы, ломающие старую версию приложения, требуют отдельного плана отката; автоматический downgrade не обещается.

Перед публичным запуском обязательны HTTPS, секреты в окружении хоста, база с постоянным хранением, резервная копия и проверка восстановления на отдельной БД. Восстановление ответа после обрыва HTTP не заменяет резервное копирование. Для демо исходное предложение — ежедневная резервная копия и хранение 7 последних; потеря данных после последней копии возможна, более строгие RPO/RTO не заявлены. Логи содержат request_id, маршрут, статус, длительность и безопасный код ошибки; тела ответов пользователя и секреты не логируем.

## 11. Критерии приёмки и проверки

| Область | Проверки для реализации |
| --- | --- |
| Контент | Все 5 исходных текстов сохранены; N=8/14/20/26/31; пороги 1/2/4/5/6; апострофы/регистр/повторы/код/дефисы и пустой текст; неизменность опубликованной версии |
| Алгоритм | Все 6 конечных маршрутов, граница ровно 20%, значения 0 и N, максимум 4 текста; оба исхода уточнения сохраняют разные reason_code |
| Валидация | Пустой неявный ответ, mode-конфликт, повторяющиеся и чужие word_id, слишком большой запрос, неверный content_version; отсутствие изменений БД после отказа |
| Транзакции | Два одновременных начала дают один run; одинаковые ответы дают один переход; повтор start с 10 неизвестными после перехода на simplified с N=8 принимается по исходному start; разные ответы одного шага — один успех и один 409; сбой до коммита и потеря ответа после коммита |
| Выбор | Рекомендация неизменяема, selected_level меняется отдельно; устаревшее изменение не затирает более новое |
| Доступ | Чужие run/step, угадываемый UUID, истёкшие/отозванные cookie, CSRF/Origin, подмена user_id, чужой claim; неверные действия не раскрывают скрытые данные |
| Регистрация | Уникальность логина при гонке; атомарность user/run/auth; действующая auth-cookie запрещает регистрацию без изменений; потерянный Set-Cookie восстанавливается входом, без нового прохождения |
| Привязка | Явный claim, повтор после потерянного ответа, чужой владелец, гонка двух аккаунтов за run, сохранение старого результата и корректный current_run_id |
| Браузер | Выбор/снятие повторов, явный all_known, клавиатура, мобильный экран, обновление до/после отправки, две вкладки, ошибка сети, отказ от регистрации, новый вход |
| Миграции/эксплуатация | Чистая БД → миграции → импорт; повторный импорт; восстановление резервной копии; лимиты reverse proxy и отсутствие секретов в логах |

Unit-тесты проверяют чистые правила на синтетических данных. API/транзакционные тесты запускаются на настоящей PostgreSQL с отдельными соединениями для гонок. HTTPX проверяет серверные контракты; Playwright — несколько полных пользовательских маршрутов, ошибки сети и обновление страницы. Выбор дополнительных тестовых библиотек и точные команды включаются в план.

CI сохраняет Ruff, форматирование и mypy, добавляет pytest с PostgreSQL, проверку миграций/контента, TypeScript typecheck и production build, минимальные браузерные сценарии. Локальные и CI-команды одинаковы и описаны в README. Тестовые accounts синтетические. Успех CI утверждается только после реального запуска; сейчас проверен дизайн, не приложение.

## 12. Утверждённые решения и оставшиеся вопросы

Языковые правила, карта рекомендаций, пояснения и контрольные числа определены агентом по поручению пользователя; отдельных вопросов о них не требуется.

Утверждены в составе технического решения: PostgreSQL/SQLAlchemy/Alembic и React/TypeScript/Vite, серверные cookie-сессии, логин/пароль без восстановления на первом этапе, сроки анонимного хранения и границы демонстрации. FastAPI уже выбран. Пошаговый план с файлами, зависимостями и проверками подготовлен в docs/plan.md и согласован пользователем; реализация выполняется по шагам. Конкретный хост, домен и бюджет не утверждены.

Реализатор самостоятельно уточняет имена модулей, конкретные версии совместимых пакетов, небольшие детали UI и настройки тестов. Существенное изменение архитектуры, объёма или подключения платных сервисов не относится к этим деталям.

## 13. Основания и проверенные источники

- [FastAPI: sync/async](https://fastapi.tiangolo.com/async/) — обработчики с блокирующими библиотеками; [security reference](https://fastapi.tiangolo.com/reference/security/) — cookie dependency извлекает токен, но не реализует жизненный цикл сессии; [password hashing](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/) — pwdlib/Argon2. JWT из примера не переносится в наш дизайн автоматически.
- [SQLAlchemy: Session basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html) и [transactions](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html) — отдельная сессия и явные границы транзакции. PostgreSQL-блокировки/ограничения должны быть проверены интеграционными тестами.
- [React: структура состояния](https://react.dev/learn/choosing-the-state-structure) и [сохранение/сброс состояния](https://react.dev/learn/preserving-and-resetting-state) — локальное состояние и сброс по ключу шага.
- [OWASP: сессии](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) — непрозрачные случайные токены, cookie-флаги и смена идентификатора при аутентификации.
- [OWASP: CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) — серверный CSRF-токен и проверка источника запроса.

Документация FastAPI, SQLAlchemy и React получена через Context7; методические источники приведены в контентном документе. Конкретные параметры продукта, сроки, порог и выбранные упрощения — наши проектные решения, а не предписания этих источников.
