**Цель:** работающий сайт с анонимным адаптивным подбором сложности, восстановлением прохождения, рекомендацией и необязательным сохранением в аккаунт.

**Архитектура:** один FastAPI-сервис с чистыми правилами онбординга и синхронными транзакциями PostgreSQL. React получает авторитетное состояние через JSON API; production работает на одном HTTPS-origin. Контент версионируется независимо от прохождений.

**Стек:** Python 3.13, uv, FastAPI/Pydantic, PostgreSQL, SQLAlchemy 2/psycopg 3, Alembic, pwdlib/Argon2; React/TypeScript/Vite; Ruff, mypy, pytest, HTTPX, Playwright, GitHub Actions.

**Основание:** [утверждённый дизайн](design.md), [правила и тексты](onboarding-content.md), [проверка дизайна](design-validation.md). Прежний план настройки исключён из Git по решению пользователя. Полный курс и уроки не входят.

## Общие ограничения

- Python `>=3.13,<3.14`; сохраняем uv, Ruff, mypy, pytest и существующие проверки CI.
- Пять текстов v1 сохраняются дословно. Версии: `onboarding-v1`, `surface-v1`, `routing-v1`; исходный порог 20, сравнение `100 * U <= threshold_percent * N`.
- Максимум четыре текста; шесть конечных маршрутов, четыре рекомендации; оба исхода simplified различаются reason_code.
- Сервер проверяет владение, слова, переходы и revision; клиент не вычисляет результат. Ответы и опубликованный контент неизменяемы.
- Логин 3–32 ASCII `[a-z0-9_]` после trim/lower; пароль 15–128 символов без нормализации. Восстановления пароля пока нет.
- Сессии: 32 случайных байта, в БД SHA-256, срок 7 суток без продления. Не привязанные run удаляются спустя 30 дней после истечения. Аккаунтные результаты сохраняются.
- JSON не больше 16 KiB; лишние поля запрещены. Origin и CSRF обязательны по правилам дизайна; токены и пароли не попадают в логи и sessionStorage.
- Блокировки: browser_sessions по ID → users → onboarding_runs по ID; доступ и сроки повторно проверяются внутри транзакции. Session отдельная на запрос, блокирующие обработчики — `def`.
- Хост, домен, бюджет и PostgreSQL major для публикации пока не выбраны. Для локального этапа фиксируем одну поддерживаемую major после проверки совместимости; перед размещением используем её же либо отдельно проверяем смену.
- Имена файлов и интерфейсов ниже соответствуют пакету `english_for_developers`; имя публичного репозитория пока сохраняется прежним.
- Перед каждой задачей проверяем рабочую копию и актуальные локальные документы. Завершаем обновлением STATUS с фактическими проверками. Не устанавливаем зависимости и не пишем продуктовый код до согласования этого плана.

## Что проверить особенно

1. Повтор start с 10 неизвестными после перехода на simplified (N=8) валидируется по исходному step_id — задача 4.
2. Гонки проверяются отдельными PostgreSQL-соединениями с синхронизацией начала операций; SQLite и последовательные вызовы не доказывают корректность — задачи 2, 4–6.
3. Потерянный HTTP-ответ после коммита отличается от отката до коммита; отдельно проверить оба случая — задачи 4–6, 8.
4. Потеря первой auth-cookie восстанавливается входом, регистрация при действующей auth запрещена — задачи 5, 8.
5. Старый HTTP-ответ и старый sessionStorage-черновик не перезаписывают новую revision/шаг; отказ хранилища не ломает UI — задачи 7–8.

## Общие команды и правило завершения

После каждой Python-задачи: `uv run --locked ruff check .`, `uv run --locked ruff format --check .`, `uv run --locked mypy src/english_for_developers`, относящиеся тесты. Полный suite: `uv run --locked pytest tests -q`. После появления БД тестам необходима отдельная PostgreSQL и TEST_DATABASE_URL; fixture не должна чистить рабочую DATABASE_URL.

С задачи 2 локально работают `uv run --locked alembic upgrade head`, `uv run --locked alembic check` и CLI проверки/импорта; команды и настройка TEST_DATABASE_URL описаны в README. С задачи 7 из frontend: `npm ci`, `npm run typecheck`, `npm run build`, `npm run test:e2e` — будущие команды, появятся с реализацией frontend.

В каждой задаче цикл: отрицательный тест → подтверждённое падение → минимальная реализация → успешная проверка → документация. Не добавлять тесты ради каркаса. Результат без проверки не помечать готовым. Commit/push и новая публичная публикация требуют соответствующего запроса; их отсутствие отдельно отражать, не скрывать за локальным успехом.
