# Продуктовый сценарий и проверка пользы

## Согласовано 2026-11-10

Первая версия сверяет заказы и успешные платежи одного интернет-магазина из файлов фиксированного формата. Схемы колонок, правила сопоставления и границы периода ещё предстоит согласовать. Возвраты не входят в первый сквозной сценарий.

Пользователь загружает две выгрузки и получает объяснимый результат: совпадения и расхождения с указанием исходных записей. Защита от повторной загрузки и валидация данных — часть требований; детали будут в дизайне сервиса.

## Согласованные правила сверки

- Один заказ может иметь несколько успешных платежей.
- Суммируем уникальные успешные платежи заказа и сравниваем сумму со стоимостью заказа; разные валюты не складываем.
- Пример: заказ 2400 ₽, платежи 1000 ₽ и 1400 ₽ — сумма совпадает; 1000 ₽ и 1000 ₽ — недоплата 400 ₽; 1000 ₽ и 1600 ₽ — переплата 200 ₽.
- Несколько платежей сами по себе не являются дублем. Для каждого платежа обязателен `payment_id`.
- Повтор с тем же `payment_id` и одинаковыми данными учитывается один раз. Тот же ID с другой суммой или другим заказом — конфликт данных, а не новый платёж.
- При конфликте ранее загруженный платёж не перезаписываем. Сохраняем конфликтующую запись для разбора, затронутый заказ отмечаем как требующий проверки. При разных заказах в версиях платежа правило для обоих заказов уточним в дизайне.

## Согласованное поведение импорта

- Частичный импорт: корректные строки загружаем, проблемные сохраняем с причинами. Пользователь не обязан вручную дописывать отсутствующие сведения.
- Нечитаемый файл или невозможность определить обязательные колонки останавливает импорт целиком. Ошибка отдельной строки не отменяет корректные строки.
- Сохраняем исходный файл и отчёт: номер строки, поле, причина, исходное значение. Отчёт доступен пользователю; технические логи его не заменяют. Полное содержимое файлов в технические логи не пишем.
- Раздельно показываем число загруженных, проблемных и повторных строк. При проблемных строках импорт завершён с предупреждениями.
- При пропущенных данных результат сверки явно помечается как неполный: недоплата может быть следствием пропущенного платежа и не является автоматически подтверждённой бизнес-ошибкой.
- Корректный платёж с неизвестным заказом загружаем: это расхождение сверки, не ошибка формата.
- Недостающие суммы и идентификаторы не придумываем. Однозначные преобразования допустимы только по явным согласованным правилам.
- Повторная обработка проблемных строк и конфликт нескольких версий нового payment_id внутри первого файла ещё требуют детализации в дизайне.

## Последующие этапы

Профили импорта позволят сопоставлять колонки магазина с общей моделью и задавать разрешённые преобразования сумм, дат, кодировок и статусов с предпросмотром и ошибками. Перспектива — отдельное пространство магазина с данными и настройками. Это направление развития, не реализованная функция и не основание сейчас строить универсальный конструктор.

Сопоставления колонок недостаточно для произвольных источников: строка может означать заказ, позицию заказа или выплату с удержанной комиссией. Поддерживаемые смыслы операций определяем явно. Возвраты, комиссии и поздние данные добавляем после согласования соответствующих правил.

## Два уровня проверки

1. Корректность реализации: синтетические файлы с заранее известными результатами; сквозной путь загрузка → сохранение → сверка → отчёт. Проверяем также ошибки данных, повторы и сохранение результатов после перезапуска.
2. Продуктовая полезность: согласованный пилот на обезличенных выгрузках магазина за закрытый период и его ручной сверке. Сотрудник подтверждает расхождения; сравниваем найденные проблемы, ложные срабатывания, время работы и объяснимость.

Тесты не доказывают коммерческую пользу. Пилот не проведён, партнёр и реальные данные не предоставлены, числовые цели не установлены. Реальные данные не публикуются в открытом репозитории. БД, интерфейс и стек приложения ещё не утверждены.
