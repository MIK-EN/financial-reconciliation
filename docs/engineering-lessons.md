# Инженерные уроки проекта

Этот файл хранит только повторно применимые выводы, подтверждённые кодом, тестами, ревью или документацией. Для каждого вывода указываем контекст и доказательство, чтобы не переносить правило туда, где оно неприменимо.

Это банк решений проекта вместе с `docs/decisions.md`: сюда — инженерные и процессные подходы (что сработало и что отвергнуто), туда — принятые решения по продукту и архитектуре. Читать перед этапом, перед брифом исполнителю и на нетривиальной развилке.

## Успешные подходы

### Операционный прогон на реальном стеке вместо веры отчёту исполнителя

- **Контекст:** задача 9, nginx-лимиты, логи, backup/restore, написанные дешёвой моделью.
- **Подход:** поднять настоящий compose-стек и проверить живыми запросами: серия POST до 429 и `Retry-After`, GET и не лимитируемые маршруты, подделанный `X-Forwarded-For`, grep логов по секретам; backup → restore в пустую БД → второй backend на ней → вход и побайтовое сравнение результата.
- **Основание:** 2026-11-18, всё совпало; два дефекта нашли только такой проверкой или чтением diff: логгер без handler в production молчал, а подсказка `openssl rand -base64` ломала бы `DATABASE_URL`.
- **Повторное применение:** для конфигурации, которую нельзя проверить unit-тестом, делать прогон с синтетическими данными и фиксировать наблюдаемые коды ответов, а не пересказ исполнителя.

### Rollback-тест доказывает запись до точки сбоя

- **Контекст:** проверка атомарности транзакции при исключении до commit.
- **Подход:** в hook перед commit выполнить настоящий flush, Core SELECT той же connection подтвердить все ожидаемые изменения, затем инъецировать ошибку; после ответа сравнить полный snapshot через новую Session и проверить успешный повтор.
- **Основание:** claim после flush дал безопасные 500/503 и полный откат; мутация `commit → та же ошибка` была обнаружена snapshot-проверкой.
- **Повторное применение:** различать откат до commit и потерю ответа после commit; ORM identity map не использовать как единственное доказательство записи.

### Конкурентную цепочку доказывает PostgreSQL, а не задержка теста

- **Контекст:** два HTTP-запроса с разными SQLAlchemy Session конкурируют за один ресурс.
- **Подход:** синхронизировать начало barrier, удерживать целевую строку внешним `FOR UPDATE` и наблюдать реальные PostgreSQL PID/`pg_blocking_pids`; после commit победителя сравнить полный snapshot до и после проигравшего.
- **Основание:** claim двух аккаунтов проверен для трёх взаимных положений UUID; ровно один 200, второй 404, дополнительной записи после проигравшего нет.
- **Повторное применение:** не использовать случайный `sleep`; задавать конечные таймауты barrier, SQL, events и futures, а порядок UUID варьировать, если строки блокируются сортировкой.

### Идемпотентный retry сначала проверяет уже записанный результат операции

- **Контекст:** изменяющая операция сама отзывает credential, необходимый для первого выполнения, а HTTP-ответ может потеряться после commit.
- **Подход:** под блокировками сначала установить действующего auth-owner и связь ресурса с исходной guest-session; если операция уже принадлежит тому же owner, вернуть актуальное состояние без повторной записи и без восстановления старого указателя current.
- **Основание:** claim retry с revoked guest возвращает 200 без изменения snapshots; после более нового claim прежний retry не меняет `users.current_run_id`.
- **Повторное применение:** отделять доказательство уже совершённой операции от предусловий новой записи; остальные auth/CSRF/expiry проверки сохранять.

### `no-store` для чувствительного маршрута задаётся общим middleware

- **Контекст:** API-операции, возвращающие состояние аккаунта или прохождения, включая ошибки до входа в handler.
- **Подход:** распознавать чувствительный method/path в общем middleware и ставить `Cache-Control: no-store` на успешные и ошибочные ответы.
- **Основание:** матрица claim подтвердила заголовок для 200/401/403/404/409/410/422/413/500/503 после расширения `_requires_no_store`.
- **Повторное применение:** при добавлении нового чувствительного маршрута проверять не только happy path, но и ранний body-limit, validation и общие exception handlers.

### Полный PostgreSQL suite использует два URL окружения

- **Контекст:** локальный запуск всего `pytest` для API- и integration-тестов.
- **Подход:** направлять и `DATABASE_URL`, и `TEST_DATABASE_URL` на одну и ту же disposable БД с суффиксом `_test`; первый использует создаваемое FastAPI-приложение, второй — интеграционные фикстуры.
- **Основание:** с обоими URL baseline задачи 6 дал 378 passed, а первый claim-прогон — 379 passed.
- **Повторное применение:** перед полным локальным suite проверять наличие обеих переменных, не выводя их значения в логи.

### Повторная проверка времени после ожидания блокировок

- **Контекст:** изменяющие операции с browser session, user и onboarding run в PostgreSQL.
- **Подход:** соблюдать общий порядок блокировок и заново получать текущее UTC-время после каждого ожидания, которое может сделать ранее проверенный срок неактуальным. После последней блокировки повторно проверять срок и доступ до записи.
- **Основание:** интеграционные проверки истечения во время register/login/logout/selection; исправление `d399dfe` прошло полный Python suite и независимое ревью.
- **Повторное применение:** использовать в claim и будущих транзакциях, где доступ зависит от срока жизни сессии или ресурса.

### Делегирование мини-шага дешёвой модели через изолированный worktree

- **Контекст:** оркестратор отдаёт механическую порцию модели OpenCode через `scripts/delegate.sh`.
- **Подход:** самодостаточный бриф с точным списком создаваемых/изменяемых файлов, запретом на остальные, примерами поведения и одной командой проверки; исполнитель работает в отдельном worktree и не коммитит. Оркестратор читает полный diff, проверяет состав файлов и сам перезапускает проверку.
- **Основание:** тестовый прогон 2026-11-18 на `opencode/deepseek-v4.1-flash-free`: два новых файла строго по брифу, отчёт в требуемом формате; самостоятельный повтор pytest (4 passed), Ruff и mypy подтвердил результат.
- **Повторное применение:** OpenCode CLI v2.3.0 поставляется внутри OpenCode.app и не лежит в PATH — скрипт находит его сам или через `OPENCODE_BIN`; флага `--dir` нет, поэтому запуск идёт из каталога worktree. Агент `worker` берётся из `.opencode/`, который должен быть в Git, иначе его нет в новом worktree.

## Неверные и отвергнутые решения

### Брифовать исполнителя платной моделью без проверки доступа к ней

- **Контекст:** первый запуск `delegate.sh` с `openrouter/openai/gpt-5.3-codex` для двух сложных порций.
- **Почему неверно:** у ключа OpenRouter закончились кредиты (`can only afford 2857 tokens`), оба запуска завершились ошибкой, не изменив файлы, при коде возврата скрипта 0.
- **Как избегать:** смотреть секцию `worker report` в выводе скрипта, а не только `EXIT`; порции со строгим TDD и подробным брифом выдержала и бесплатная `deepseek-v4.1-flash-free` (cleanup, логи, nginx, runbook), а приёмка с мутациями ловит слабости.
- **Основание:** 2026-11-18, задача 9.

### Параллельные исполнители на одной тестовой БД и слова в zsh

- **Контекст:** несколько исполнителей одновременно запускают pytest, который делает TRUNCATE тестовой БД; оркестратор в zsh хранит префикс команды в переменной.
- **Почему неверно:** одна общая `_test` БД даёт гонки между прогонами; `$PG_EXEC` в zsh не разбивается на слова и падает `command not found`, хотя bash-скрипты работают.
- **Как избегать:** выдавать каждому исполнителю отдельную мигрированную БД с суффиксом `_test`; в zsh-командах оркестратора использовать функцию или массив. Docker Desktop мог зависать на `docker pull` при рабочем curl — перезапуск Docker лечит, после него поднять dev-контейнер заново.
- **Основание:** 2026-11-18, задача 9.
### Автоматизировать клавиатуру нативного `<select>` в Playwright

- **Контекст:** e2e-проверка смены уровня клавиатурой на экране результата.
- **Почему неверно:** в Chromium на macOS ArrowDown и type-ahead на закрытом `<select>` открывают системный popup, недоступный Playwright; значение и запрос не меняются. На Linux та же клавиша меняет значение, поэтому тест зависит от платформы.
- **Как избегать:** использовать нативные элементы, доступность которых обеспечивает браузер, и не тестировать их встроенную клавиатуру; клавиатурой проверять собственные кнопки приложения.
- **Основание:** 8.1, 2026-11-18: отладка с журналом сети показала отсутствие запроса `selection` после ArrowDown и Enter.

### Проверять отсутствие состояния на элементе, который его никогда не имел

- **Контекст:** e2e-тест «после перехода не осталось отметок прежнего шага».
- **Почему неверно:** проверка `aria-pressed="false"` у слова, которое не отмечалось, проходит при любом поведении и ничего не доказывает.
- **Как избегать:** выбирать элемент, который при ошибке был бы в неверном состоянии (здесь `file`, отмеченный на шаге 1 и повторяющийся в тексте 2), и подтверждать тест мутацией.
- **Основание:** ревью делегированного `recovery.spec.ts`, 2026-11-18; слабость была в брифе оркестратора.

### Инъецировать ошибку, не доказывая достижение изменённого состояния

- **Контекст:** fault test падает до flush либо проверяет только HTTP-статус.
- **Почему неверно:** зелёный snapshot может означать, что бизнес-изменения вообще не выполнялись, а не что транзакция корректно откатилась.
- **Как избегать:** до ошибки подтвердить flushed значения через Core/другой источник вне identity map и выполнить mutation-check с настоящим commit перед ошибкой.
- **Основание:** 6.4b проверил owner, claimed_at, revision, current_run_id и revoked_at до инъекции; commit-мутация сохранила их и ожидаемо сломала тест.

### Считать ненаблюдаемую мутацию доказанной текущей гонкой

- **Контекст:** claim сначала сериализуется на общей guest-session и лишь затем блокирует run.
- **Почему неверно:** удаление `FOR UPDATE` с run остаётся GREEN в гонке двух claim, потому что более ранняя session-lock уже не допускает одновременную запись; такой тест не доказывает роль run-lock в других пересечениях операций.
- **Как избегать:** честно фиксировать ненаблюдаемую мутацию и проверять наблюдаемое бизнес-правило — единственного owner и 404 проигравшему; роль поздней блокировки проверять отдельной гонкой с другим типом операции, если она нужна.
- **Основание:** mutation-check 6.4a не обнаружил удаление run-lock, но обнаружил ослабление owner guard результатами 200/403 и 200/200 вместо 200/404.

### Отвергать отозванный операцией credential до проверки идемпотентного результата

- **Контекст:** первый claim закоммичен и отозвал guest-session, но клиент не получил успешный HTTP-ответ.
- **Почему неверно:** повтор получает 403, хотя нужное состояние уже сохранено; клиент не может отличить успешный commit от отказа до commit.
- **Как избегать:** после проверки действующего auth/CSRF разрешать revoked guest только как доказательство исходной связи уже принадлежащего тому же owner ресурса; для нового claim revoked guest по-прежнему запрещать.
- **Основание:** RED порции 6.3 — три committed retry-сценария возвращали `session_unavailable`; owner-first ветка дала безопасный 200 и неизменную БД.

### Устанавливать `no-store` только внутри endpoint handler

- **Контекст:** маршрут может завершиться в middleware, dependency или exception handler до выполнения endpoint.
- **Почему неверно:** успешный ответ получает заголовок, а ошибки 413/422/500/503 и часть отказов остаются без запрета кэширования.
- **Как избегать:** централизовать политику по method/path и покрывать тестами каждый слой завершения запроса.
- **Основание:** исходный RED порции 6.2 — 30 сценариев падали только из-за отсутствующего `no-store`; в 19 PostgreSQL-сценариях дополнительно подтверждено равенство полных snapshots.

### Полный suite только с `TEST_DATABASE_URL`

- **Контекст:** общий запуск `pytest tests -q`, включающий API-тесты, которые создают приложение без fixture override.
- **Почему неверно:** integration-тесты проходят, но приложение не получает `DATABASE_URL`; API-запросы возвращают 503 до проверки ожидаемого поведения.
- **Как избегать:** для полного suite задавать оба URL; один `TEST_DATABASE_URL` использовать только для узких наборов, которые сами подменяют настройки приложения.
- **Основание:** baseline задачи 6 с одним test URL получил 371 passed и 7 ложных 503; повтор с обоими URL — 378 passed.

### Единственная проверка срока до транзакционного ожидания

- **Контекст:** операции, которые сначала валидируют сессию, а затем ждут блокировку user или run.
- **Почему неверно:** срок может истечь во время ожидания, после чего операция продолжит работу по устаревшему значению `now`.
- **Как избегать:** тестировать границу детерминированной блокировкой или управляемыми часами и повторять проверку после ожидания; не подменять такую проверку последовательным тестом, который не моделирует продвижение времени во время операции.
- **Основание:** RED-сценарии перед исправлением `d399dfe` воспроизводили 12 нарушений временных границ.

### Принимать команды runbook только после живого прогона

- **Контекст:** runbook с командами проверки.
- **Почему неверно:** текст выглядит правильно, но команда может не сработать.
- **Как избегать:** прогонять каждую команду на реальном стеке до приёмки.
- **Основание:** прогон нашёл две ошибки - логин с дефисом и ожидаемый `401` вместо `403`.

### Хранить команду с аргументами в функции, а не в переменной (zsh)

- **Контекст:** повторяющийся `docker compose --env-file ... -f ... -f ...`.
- **Почему неверно:** zsh не разбивает значение переменной на слова, команда падает.
- **Как избегать:** функция `dc() { docker compose ... "$@"; }`, переопределять после нового входа.
- **Основание:** сессия выпуска на VPS.

### Не зависеть от одного платного провайдера модели

- **Контекст:** делегирование исполнителям через OpenRouter.
- **Почему неверно:** платная модель может внезапно не стартовать из-за исчерпанных кредитов.
- **Как избегать:** при первом отказе по кредитам сразу переходить на бесплатную модель (`opencode/longcat-2.5-free`, `opencode/deepseek-v4.1-flash-free`) и не повторять запуск.
- **Основание:** `deepseek-v4-pro` недоступна, работа завершена бесплатными моделями.

### Не объяснять сбой доступа единственной гипотезой без контрольного теста

- **Контекст:** сайт на VPS открывался с телефона без VPN, а с Mac с VPN — нет.
- **Почему неверно:** вывод «виноват служебный домен» нельзя делать, пока не проверено, что с сервера все Host-заголовки отвечают одинаково, а обрыв не происходит на пути через VPN.
- **Как избегать:** сначала контрольный тест на самом сервере (разные `Host` к `127.0.0.1`), затем с клиента без VPN и с VPN, и только потом менять домен.
- **Основание:** выпуск на VPS 2026-11-20, сеть Mac с VPN.
